# 02.1.02-S1-T4 — Invitation operational signal

## Contract

Emit a structured invitation-boundary signal with workspace and module labels. The
signal must cover both success and refusal/failure paths, be testable through an
explicit dependency, and have an operational registration/threshold record.

## Plan

1. Inspect the existing logging and server composition boundary.
2. Add one structured invitation signal with non-secret identifiers and outcome.
3. Exercise success and refusal paths through feature tests.
4. Record dashboard and on-call threshold dependencies separately from code evidence.

## Implemented evidence

- `user-invitation.service.ts` emits an explicit, dependency-injected signal after a
  successful invite and for each explicit refusal path.
- `user-invitation.telemetry.ts` writes the signal as a structured `Logger.info` event.
- The context contains `module`, `operation`, `workspaceId`, `actorId`, `outcome`, and
  the non-secret refusal reason when applicable. It intentionally contains no raw token
  or email address.
- Feature tests cover a success signal, a forbidden/refusal signal, and the logger
  adapter's structured context.

## Remaining external dependencies

The repository has no dashboard provisioning, metrics backend, alert-routing system, or
on-call rotation configuration. Therefore the following Done-when clauses are blocked
outside this workspace and cannot be truthfully marked complete:

1. Register the signal in the operational dashboard.
2. Agree and configure an alert threshold with the on-call rotation.
3. Invoke the composed HTTP boundary against a real runtime and confirm a failed run
   appears in that dashboard.

The signal adapter is ready to be injected when the story's missing authenticated
invitation route/service composition is available.
