# 01.1.04-S1-T4 — Emit the organization-branding Operate signal

## Task understanding

The Sprint 1 task record assigns this to Muhammad Salman under `Workspace · Platform`, kind `telemetry`, with four implementation steps and two cases. The task is to make organization-branding reads observable in Operate: record whether the read succeeded, how long it took, how many organizations it returned, and whether it crossed the story's 700 ms first-page budget. Keep the signal useful for operations without recording tenant IDs, organization IDs, emails, credentials, or logo URLs.

## Implementation

- Added `observeOrganizationBrandingRead` to the temporary API telemetry boundary. It emits one immutable structured event for a successful or failed organization list read.
- Signal name: `organization_branding.read`.
- Fields: `outcome`, `durationMs`, `resultCount`, `budgetMs`, and `withinBudget`.
- Uses Node's monotonic `performance.now()` clock; read errors are rethrown unchanged after emitting the failure signal.
- API composition writes successful in-budget events at info level and errors/over-budget events at warn level through the shared Pino logger.
- Added deterministic success, error, latency-budget and no-tenant-identifiers tests.

The four implementation parts are covered as follows:

1. Define the organization-branding read signal and its bounded fields.
2. Emit a success event with elapsed time and result count.
3. Emit an error event and rethrow the original read error.
4. Compare each read with the 700 ms story budget and document operational thresholds and first response.

The two automated signal cases are: a successful in-budget list read, and a failed over-budget read that contains no workspace/organization identifiers.

## Operate threshold and first response

- Product budget: list-read duration p95 must stay at or below **700 ms**, matching AC-4.
- Review the `organization_branding.read` events over a five-minute window; investigate when p95 exceeds 700 ms or error outcomes exceed 1% with at least 100 reads. Any individual error or over-budget read is also emitted at warn level for investigation.
- First response: check API/MongoDB availability and query/index health, then compare the emitted duration and result-count fields with the latest known-good window. Avoid logging or sharing tenant identifiers while investigating.
- No metrics collector or dashboard is configured in this repository yet. The structured event is the application signal for the existing log pipeline; provider-specific exporter/dashboard provisioning remains an operations dependency.

## Validation

- API route integration asserts a successful authenticated organization read emits exactly one success signal.
- Telemetry unit tests assert success, failure, the 700 ms boundary, and the bounded field set.
- Run API tests, typecheck, lint and build with the repository scripts.

## Scope

The read route itself remains the explicitly temporary T2 demo API and can be removed when real authentication/read APIs are merged. Keep the signal contract/tests and move the same observer to the permanent Workspace organization-list query at that time; do not carry the demo login or mock reader into production.
