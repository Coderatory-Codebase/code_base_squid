  and only as far as it says.
- **Squid task:** `01.4.06-S2-T1` — Honour recorded exceptions in the guardrail checks.
- **Squid state at documentation:** Planned; 0/4 steps and 0/4 task cases passing. No

## Done when

A change passes a guardrail only when an open exception covers exactly what the change
does (including EX-01 outbox appends and EX-02 Billing's entitlements copy); an expired
exception no longer permits the change.

## Backlog implementation steps

1. Read open exceptions, their scope, and expiry from `architecture/exceptions.json`.
2. Allow only the crossing named by each exception.
3. Fail when an exception has expired.
4. Add fixture cases for EX-01 and EX-02.

## Architecture, inputs, and scope

- Extend the existing repository-owned `codebase/validators/module-governance.mjs` and
  policy tests. This is CI governance work, not application/runtime behavior.
- The validator currently reads `architecture/collections.json`, where EX-01 and EX-02
  are embedded, and does not read `architecture/exceptions.json` or enforce expiry.
  T1's stated source is a dedicated `architecture/exceptions.json`; migrate the exception
  records there and make it the single source of exception status, allowed modules,
  operations/fields, transaction scope, and expiry.
- Enforce EX-01 narrowly: module code may append to `outbox` only within
  `withTransaction`; `publishedAt` updates are relay-only. Enforce EX-02 only for
  Billing updates to the `entitlements` field on Workspace-owned `workspaces` while
  EX-02 is open and unexpired.
- The inspected Squid architecture baseline supplies EX-01 expiry `2027-09-28` and
  EX-02 expiry `2027-03-28`; `architecture/exceptions.json` was synchronized to those
  values on 2026-10-06. Reconfirm with the policy owner if the baseline changes.
- The `next/*` domain guard already exists, but its current diagnostic does not include
  ARC-001. AC-3 requires the rule/decision reference in the diagnostic; add it as needed
  so the acceptance case can assert it.
- No new service, database collection, generic exception framework, UI, or third-party
  orchestrator is in scope. No exception may authorize a broader operation by default.

## Implementation and validation record

- Added `architecture/exceptions.json` as the single exception source; removed embedded
  copies from `architecture/collections.json`.
- EX-01 permits module outbox appends only inside a detected `withTransaction` callback;
  the Shared Kernel relay remains limited to `publishedAt`. EX-02 permits Billing to
  update only `workspaces.entitlements` while open.
- The guardrail validates exception ID, status, owner binding, writer binding, operation
  scope, and `expiresAt`. A date at or before the injected/current UTC date is expired
  and stops authorizing writes. Invalid expiry metadata fails policy validation.
- Added focused tests for transaction requirement, scope limitation, and expired EX-02.
- **Expiry policy data:** the repository register now carries EX-01 `2027-09-28` and
  EX-02 `2027-03-28`, matching the inspected Squid architecture baseline. The validator
  fails closed after those dates; revalidate against Squid if its source values change.

  repository check reports the known Workspace writes to Identity-owned `users` and
