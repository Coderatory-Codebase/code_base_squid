## Intended result and Done when

CI fails when a published event version loses or changes a field, and names the
event, version, and field. Adding a new version alongside the existing version
must remain allowed. A developer guide explains that versioning workflow.

## Backlog steps

1. Snapshot each registered version's schema at release 1.
2. Compare current schemas with the base snapshot on each pull request.
3. Fail with the event, version, and field that changed.
4. Document how to add a new version instead of editing a published one.

## Story context, requirements, and constraints

- **Story acceptance case 1:** add `TaskUpdated` v2 beside v1; publish both on a
  task change; a v1 consumer continues receiving v1.
- **Story acceptance case 2:** remove a field from a published version; CI fails
  and names the event, version, and field.
- **Task 1 relationship:** T1 supplies the envelope/registry and overlap helper.
  T2 supplies the compatibility guard needed to verify the story's second case.
  Squid does not show a formal T1-to-T2 dependency edge; this is an implementation
  relationship, not a claim that the backlog links them as dependent tasks.
- **Architecture constraints:** ADR-007 and ARC-002 require a producer's state
  change and outbox record to share a transaction; ARC-006 requires consumer
  deduplication by event ID; ARC-010 keeps old/new versions flowing during the
  overlap release. This task adds only contract checking; it does not own an
  outbox, relay, producer, or consumer.
- **Payload constraint:** the backlog names Wave 1 event families and envelope
  fields but supplies no event-specific payload field schemas. The compatibility
  implementation must not invent them. It checks declared schema fields, and
  dedicated `TaskUpdated` test fixtures prove field diagnostics.

## Local implementation record

The kernel exposes JSON-schema snapshots for registered event envelope versions,
a deterministic compatibility comparer, and a CLI check. The GitHub Actions
workflow compares a pull request against the snapshot from its base commit and
checks that the branch snapshot exactly matches its current schemas; changing
the snapshot in the branch cannot hide a regression against that base.
Breaking changes are reported with event/version/field; any field change within
an existing published version is rejected, while a new version alongside the
old one is accepted. The README describes the
version overlap/release workflow. Focused kernel validation passed: typecheck,
build, lint, 11 total tests (7 compatibility and 4 T1 envelope/overlap), and the positive compatibility CLI check. The negative CLI
check failed as expected with the required event/version/field diagnostic. The
repository node-syntax check and `git diff --check` also passed. Hosted CI,
independent review, and Squid step/case recording are still pending. Squid remains
unchanged.
