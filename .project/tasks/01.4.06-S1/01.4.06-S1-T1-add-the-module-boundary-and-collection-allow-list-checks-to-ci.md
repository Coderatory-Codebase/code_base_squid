  checks to CI.

- **Record date:** 2026-10-05.

## Intended result

Every pull-request build rejects a module importing another module's private `db/`
surface or domain code importing `next/*`. It also rejects a module gateway that names
a collection owned by another module. Diagnostics identify the violating file and
modules, or the collection and its owner. A recorded open exception is honored only for
the scope it explicitly covers. A change using a published module interface and owned
collections passes.

## Backlog implementation steps

Squid lists these four steps:

1. Write `architecture/deps.json` from the module dependency list.
2. Write `architecture/collections.json` from the collections register, with one writing
   module for each collection.
3. Add a dependency-cruiser (or equivalent) job that checks imports against `deps.json`.
4. Add a check that each module's gateway names only its own collections.

The Squid Architecture Baseline provides the source inputs: its L2 module dependency
matrix and Data Design collection ownership register. These are recorded in
`architecture/deps.json` and `architecture/collections.json`; the manifests retain the
source label and only the two recorded open exceptions (EX-01 and EX-02).

## Architecture and scope

- Scope is repository build governance/control-plane validation, not application runtime
  behavior. The root `AGENTS.md` says the control plane owns repository policy and
  orchestration and custom checks are for repository-specific architecture/governance.
- `codebase/validators/architecture-boundaries.mjs` already enforces existing workspace,
  feature, and public-surface rules. Inspect and extend the narrowest suitable existing
  validator or introduce a tool only if the current control plane cannot express the
  required checks. Squid permits dependency-cruiser **or equivalent**.
- Keep dependency direction explicit and data-driven. Collections have exactly one
  writing owner. Any exception must be recorded, open, and limited to its stated scope.
- CI must run the guardrails for every pull request and fail clearly if required policy
  inputs or tools are missing or cannot execute.
- Do not add runtime services, database collections, mock application dependencies, or
  user-interface changes for this task.
