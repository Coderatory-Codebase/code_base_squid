## Intended result

An event version can be removed only after its required one-release overlap has elapsed and no consumer still uses it. A rejected retirement must identify the event/version and the applicable release or remaining consumer. The registry must retain enough lifecycle information to make this decision reproducible.

## Backlog steps

Squid lists these four implementation steps:

1. Record the release each version was superseded in.
2. List the consumers of each version from the registry.
3. Make CI refuse removing a version still consumed or inside its overlap.
4. Note the retirement in the kernel contract’s Events clause.

## Implementation and validation record

### Code written

- Added a release-aware lifecycle registry view for active event versions, with explicit override records for supersession releases and consumer module names. Retained historical entries can remain in the overrides after a version is removed from the active contract registry.
- Added a fail-closed retirement decision: removal is rejected when lifecycle data is missing, the current release is the supersession/overlap release, or consumers remain. The rejection includes the event/version and the reason; early removal reports the earliest eligible release.
- Recorded the existing `TaskUpdated` v1/v2 overlap as beginning in `R1.0`, matching the checked-in schema snapshot. The repository has no registered production consumer modules, so its current consumer list is empty; this does not assert that external consumers have migrated.
- Wired the decision into the existing schema compatibility comparison. A retired version is accepted only when the lifecycle gate allows it; incompatible field changes remain rejected by the existing comparison.
- The release/consumer acceptance cases are owned and documented under T2 in `tests/retirement-acceptance.test.ts`; T1 supplies the guard those checks exercise.
