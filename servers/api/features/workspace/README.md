# Workspace feature contract and runbook

## Module contract

- `GET /organizations` requires a valid bearer session and returns `{ organizations: [{ id, name }], nextOffset }`. The API fetches at most 51 rows to return a fixed 50-item page and only provides `nextOffset` when more results exist. Subsequent pages use the returned offset (`?offset=50`, etc.); invalid offsets are rejected.
- The query includes live organizations owned by the principal or connected to one of the principal's workspace IDs. Deleted and unrelated organizations are excluded. Results sort by most recently used, then name.
- Ordering includes organization ID as a stable final tie-breaker. Owner, workspace membership, and direct organization membership have list-page indexes to support the filter/order shape. Only `_id` and `name` are projected; team, invitation, and audit-log data are not transferred for list rendering.
- Organization-level memberships are also included in `/organizations`; this repository does not yet define a first-class Workspace entity or workspace-scoped role source.
- `POST /organizations` requires a valid bearer session and a trimmed name from 1 to 80 characters. The organization policy must allow `organization:create` for the authenticated principal before persistence runs.
- Creation records the authenticated creator as `ownerId` in the same organization document; the new organization starts with no workspace links or other members.
- `GET /organizations/:organizationId/dashboard` returns the caller's organization role, team membership, linked-workspace count, and the ten most recent team-management audit events. It reads uncached persisted data.
- Owners and admins may create admin/member invitations, change member roles, and remove members. Owners cannot be demoted or removed. Member-only requests to management routes return `403`.
- Invitation links are generated from the configured `WEB_ORIGIN`; tokens are random, stored only as SHA-256 hashes, expire in seven days, are single-use, and can only be accepted by an authenticated account whose email matches the invitation. Email delivery is intentionally not configured; the manager copies the generated link.
- Memberships, pending invitations, and the last 50 team-management audit events are stored in the organization document so invite acceptance and its event are atomic single-document updates. Expired/accepted invitation entries are pruned when a new invite is created.
- The feature owns its Organization model and query gateway. Authentication owns User and Session models; session tokens are random, only their SHA-256 hashes are stored, and sessions expire after eight hours.
- The web app reads its `workspace_session` HttpOnly cookie in the Server Component and calls the API through `apps/web/features/organizations/organizations.gateway.ts`. The token is sent in the server-to-server request and is not read by client JavaScript.

## Signals, dashboard, and thresholds

Every `/organizations` request, including dashboard/team routes, emits `organization.request.signal` with `workspace=Platform`, `module=workspace`, operation, status, outcome, and `durationMs`, including 4xx/5xx responses. Valid organization-list requests include `pageOffset`, allowing the first-page p95 to be isolated. The Grafana dashboard definition is `enablers/observability/workspace/organization-dashboard.json`; it charts request volume, error rate, organization request p95, and first-page list p95 from the API's structured JSON logs. Import it into the Grafana instance connected to the central Loki log source to make it visible.

The machine-readable alert policy is `enablers/observability/workspace/organization-alert-policy.json`. It proposes an error rate above 5% for five minutes (minimum 20 requests), organization request p95 above 700 ms, and organization setup p95 above 300 ms for five minutes. **On-call ratification is still pending**; do not enable paging until the workspace rotation records its approver and approval date in that file. Central log-platform owners must enforce the stated 30-day telemetry retention. These external operational actions cannot be completed by repository changes alone.

## Runbook

For 401 responses, sign in again and confirm the session exists and has not expired. For 403 management responses, check the caller's organization role; only owners/admins may mutate team access. Invalid or expired invitation links require a fresh invitation to the matching account email. For 5xx responses or elevated error rate, inspect the dashboard's error rate and request logs, then check `/health` and MongoDB connectivity. For organization-list p95 above 700 ms, run `pnpm --filter @workspace/api measure:organization-budget`; it seeds 500 direct organization memberships for one principal, measures the first 50-item page across 200 loopback HTTP requests to `GET /organizations`, checks `member_list_page` in the explain plan, and writes a dated result under `servers/api/performance-results/`. Later pages are fetched by the list's scroll sentinel (with a keyboard-accessible Load more control); `nextOffset: null` means the list is complete and no further request is made. For setup p95 above 300 ms, run `pnpm --filter @workspace/api measure:organization-setup-budget`; it sustains 20 loopback `POST /organizations` requests per second for ten minutes against a separate in-memory MongoDB and records the result. For dashboard p95 above 700 ms or payload above 100 KiB, run `pnpm --filter @workspace/api measure:workspace-dashboard-budget`; it seeds 21 members, ten linked workspaces, and 50 activity records, then sends 200 isolated loopback requests. All measurement commands use disposable in-memory MongoDB and never modify a configured database.

## Security and isolation checks

`servers/api/features/workspace/tests/organization.gateway.test.ts` verifies owner and workspace membership scoping, deletion filtering, unrelated-tenant exclusion, sorting, and index use. `servers/api/tests/collection-allow-list.test.ts` pins the current Mongoose collection set (`organizations`, `sessions`, `users`). Organization command tests verify that missing, denied, wrong-action, and wrong-subject policy decisions cannot reach persistence.
