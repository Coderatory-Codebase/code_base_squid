# Workspace feature contract and runbook

## Module contract

- `GET /workspace/organization-settings` requires a valid bearer session and returns
  `{ settings: [...] }` for organizations owned by the principal or connected to one of
  the principal's workspace IDs. This lets an owner set defaults before creating or
  linking a workspace. Each row includes its identifier, name, optimistic version, and an
  owner-only `canUpdate` flag alongside the normalized values. The query excludes
  soft-deleted organizations and uses the owner/workspace settings covering indexes. The
  web Server Component calls this API
  through a server-only adapter using the `workspace_session` HttpOnly cookie; the session
  token is not read by client JavaScript. An empty result links to organization setup, and
  an API failure renders an error with a retry link.
- `GET /organizations` requires a valid bearer session and returns `{ organizations: [{ id, name }], nextOffset }`. The API fetches at most 51 rows to return a fixed 50-item page and only provides `nextOffset` when more results exist. Subsequent pages use the returned offset (`?offset=50`, etc.); invalid offsets are rejected.
- The query includes live organizations owned by the principal or connected to one of the principal's workspace IDs. Deleted and unrelated organizations are excluded. Results sort by most recently used, then name.
- Ordering includes organization ID as a stable final tie-breaker. Owner, workspace membership, and direct organization membership have list-page indexes to support the filter/order shape. Only `_id` and `name` are projected; team, invitation, and audit-log data are not transferred for list rendering.
- Organization-level memberships are also included in `/organizations`. Workspace invitation acceptance is owned by the Workspace feature; its Mongo-backed consumer records active memberships and event receipts in the `workspaces` collection. Workspace creation and invitation-event production remain owned by their respective flows.
- `GET /organizations` requires a valid bearer session and returns `{ organizations: [{ id, name, status, archivedAt }], nextOffset }`. Archived organizations remain visible and readable with `status: "archived"`. The API fetches at most 51 rows to return a fixed 50-item page and only provides `nextOffset` when more results exist. Subsequent pages use the returned offset (`?offset=50`, etc.); invalid offsets are rejected.
- `POST /organizations` requires a valid bearer session and a trimmed name from 1 to 80 characters. The organization policy must allow `organization:create` for the authenticated principal before persistence runs.
- Creation records the authenticated creator as `ownerId` in the same organization document; the new organization starts with no workspace links or other members.
- `GET /organizations/:organizationId/dashboard` returns the caller's organization role, team membership, linked-workspace count, and the ten most recent team-management audit events. It reads uncached persisted data.
- Owners and admins may create admin/member invitations, change member roles, and remove members. Owners cannot be demoted or removed. Member-only requests to management routes return `403`.
- Invitation links are generated from the configured `WEB_ORIGIN`; tokens are random, stored only as SHA-256 hashes, expire in seven days, are single-use, and can only be accepted by an authenticated account whose email matches the invitation. Email delivery is intentionally not configured; the manager copies the generated link.
- Memberships, pending invitations, and the last 50 team-management audit events are stored in the organization document so invite acceptance and its event are atomic single-document updates. Expired/accepted invitation entries are pruned when a new invite is created.
- `PATCH /organizations/:organizationId/lifecycle` supports owner-only archive, restore, and soft-delete transitions. Each request supplies `expectedVersion`; stale writes return `409` with the current lifecycle state. MongoDB applies the owner, live-state, and version predicates atomically. Archived organizations stay readable but team-management writes are refused. Soft deletion is retained indefinitely until a retention period is approved; no archive or delete action purges data. The idempotent schema/index migration is `servers/api/migrations/20261007-organization-deletion-archive.ts`.
- The feature owns its Organization model and query gateway. Authentication owns User and Session models; session tokens are random, only their SHA-256 hashes are stored, and sessions expire after eight hours.
- Organization settings remain in `organizations.settings`. The model validates the supported time zone, week-start, date-format, and workspace-setup-rule values while preserving unknown legacy settings. An explicit `version` field supports optimistic concurrency; the version backfill and rollback are defined in `integrations/migrations/20261007-organization-setting.ts`.
- Workspace is the sole owner of organization settings state; the settings live in the existing `organizations` collection and use the `workspace_settings_live_cover` and `owner_settings_live_cover` indexes for scoped reads. Settings follow the organization lifecycle: soft-deleted organizations disappear from live reads, but their setting values remain stored with the organization for recovery/audit; there is no independent TTL or settings purge. Any eventual physical organization purge must follow the owning organization's approved retention process.
- The covered workspace settings index includes `_id`, `ownerId`, `version`, and `name` so the server-rendered read can provide safe edit metadata and identify each organization without fetching full organization documents. Apply `integrations/migrations/20261007-organization-settings-edit-cover.ts` for the workspace index and `integrations/migrations/20261008-organization-settings-owner-read.ts` for the owner read and name projection; each migration documents its rollback.
- The pure `domain/organization-setting.ts` rule treats missing or legacy-null settings as no overrides, resolving to UTC, Monday, `DD/MM/YYYY`, and `any member`; it preserves valid overrides and returns a typed error for an invalid stored value. The settings gateway uses that rule and logs read failures at the infrastructure boundary.
- Organization-default updates use the `workspace.organization-settings.update` command and the central `organization.settings.update` ability. Workspace policy allows only a non-guest owner; members without owner rights, guests, API keys, and commands without an attached policy decision are refused before a handler runs. The async actor resolver is a request-scoped authorization lookup, not a background job. The dependent update handler must build a policy-bound command and dispatch it through the command bus.
- `PATCH /organizations/:organizationId/settings` requires a bearer session, a positive `expectedVersion`, and at least one supported setting. The Workspace application service resolves the caller's organization role and dispatches a policy-bound update command. Successful writes return the normalized values and incremented version; stale writes return `409` with the current normalized values and version. The web server action and `PATCH /api/workspace/organization-settings/:organizationId` route use this same API contract.
- Invalid settings return `400` with `status: "invalid_value"`, the rejected field, and its accepted values (time zones are described as valid IANA identifiers). Existing workspace records are not rewritten when organization defaults change. Creating future workspaces from these defaults belongs to the workspace-setup consumer flow, which is not implemented in this module yet.
- The organization settings page keeps server-rendered loading/empty/error states and mounts an owner-only client editor for the interactive controls. It previews pending values with `useOptimistic`, falls back to the last confirmed values on update failure, and on `409` shows the current server values with choices to accept them or reapply the user's edits against the current version. Native labeled fields and buttons preserve keyboard order and use visible focus rings with light/dark theme colors; status and conflict messages are announced to assistive technology.
- The web app reads its `workspace_session` HttpOnly cookie in the Server Component and calls the API through `apps/web/features/organizations/organizations.gateway.ts`. The token is sent in the server-to-server request and is not read by client JavaScript.

## Signals, dashboard, and thresholds

Organization-settings reads emit `Organization settings read completed.` or
`Organization settings read failed.` structured log events with `module=workspace`,
`feature=organization-settings`, `operation=read`, workspace IDs, outcome, and duration;
failures also include a reason. The gateway tests verify the failure signal. The dashboard
includes settings read volume, failures, and p95 panels. A 700 ms p95 target for 200 workspace organizations and
200 requests is now recorded as `organizationSettingsView` in `architecture.yaml`; it is
separate from the `organizationList` budget for `/organizations`.

Every `/organizations` request, including dashboard/team routes, emits `organization.request.signal` with `workspace=Platform`, `module=workspace`, operation, status, outcome, and `durationMs`, including 4xx/5xx responses. Valid organization-list requests include `pageOffset`, allowing the first-page p95 to be isolated. The Grafana dashboard definition is `enablers/observability/workspace/organization-dashboard.json`; it charts organization request signals and organization-settings read volume, failures, and p95 from the API's structured JSON logs. Import it into the Grafana instance connected to the central Loki log source to make it visible.

The `InvitationAccepted` workspace consumer emits `Invitation acceptance consumer signal.` for each handled event with the event/workspace IDs, outcome, and duration. Its per-event latency threshold is 5 seconds; over-threshold and failed signals are warnings. The dashboard and proposed alert policy include this signal. The consumer applies the role supplied by the accepted invitation event (and forces guests to the `guest` role), and atomically stores the event receipt with membership or the `ARCHIVED` refusal in the `workspaces` document, so retries cannot duplicate the operation. The event-producing invitation-acceptance flow and queue worker are not present in this repository yet; no live event delivery or 5-second production measurement is claimed.

`PATCH /organizations/:organizationId/settings` uses the same boundary signal with `feature=organization-settings` and `operation=update`; both successful writes and HTTP failures include status, outcome, and duration. The dashboard includes update outcome and p95 panels. The proposed update alert thresholds are error rate above 5% over five minutes (minimum 20 requests) and p95 above 700 ms over five minutes; both await workspace on-call ratification. For elevated update errors, separate expected `409` version conflicts from `401` session failures, `403` owner-policy refusals, and `5xx` persistence failures before taking action. For update p95 above 700 ms, inspect MongoDB latency and the `organizationId + ownerId + deletedAt + version` conditional write path; do not retry a stale version without first refreshing the current values.

The machine-readable alert policy is `enablers/observability/workspace/organization-alert-policy.json`. It proposes an error rate above 5% for five minutes (minimum 20 requests), organization request p95 above 700 ms, organization setup p95 above 300 ms, and organization-settings read p95 above 700 ms for five minutes. **On-call ratification is still pending**; do not enable paging until the workspace rotation records its approver and approval date in that file. Central log-platform owners must enforce the stated 30-day telemetry retention. These external operational actions cannot be completed by repository changes alone.

## Runbook

For a refused organization-default update, inspect the resolved caller's role and guest/API-key classification, then confirm the command was built with the `organization.settings.update` decision before it reached the command bus. For `409` from a settings update, reload the current settings and version and resubmit the user's intended change against that version. Never retry the old version automatically. The update filters by organization ID, authenticated owner ID, live (`deletedAt: null`) state, and expected version; a mismatch returns the current value only within that same owner scope.

For 401 responses, sign in again and confirm the session exists and has not expired. For 403 management responses, check the caller's organization role; only owners/admins may mutate team access. Invalid or expired invitation links require a fresh invitation to the matching account email. For 5xx responses or elevated error rate, inspect the dashboard's error rate and request logs, then check `/health` and MongoDB connectivity. For organization-settings update p95 above 300 ms, run `pnpm --filter @workspace/api measure:organization-settings-updates-budget`; it sends owner updates at 20 requests per second for ten minutes against a disposable in-memory MongoDB and writes a dated result under `servers/api/performance-results/`. For organization-settings read p95 above 700 ms, run `pnpm --filter @workspace/api measure:organization-settings-budget`; it seeds 200 organizations in a disposable in-memory MongoDB, issues 200 loopback HTTP requests to `GET /workspace/organization-settings`, verifies the `workspace_settings_live_cover` index, and writes a dated result under `servers/api/performance-results/`. For organization-list p95 above 700 ms, run `pnpm --filter @workspace/api measure:organization-budget`; it seeds 500 direct organization memberships for one principal, measures the first 50-item page across 200 loopback HTTP requests to `GET /organizations`, checks `member_list_page` in the explain plan, and writes a dated result under `servers/api/performance-results/`. Later pages are fetched by the list's scroll sentinel (with a keyboard-accessible Load more control); `nextOffset: null` means the list is complete and no further request is made. For setup p95 above 300 ms, run `pnpm --filter @workspace/api measure:organization-setup-budget`; it sustains 20 loopback `POST /organizations` requests per second for ten minutes against a separate in-memory MongoDB and records the result. For dashboard p95 above 700 ms or payload above 100 KiB, run `pnpm --filter @workspace/api measure:workspace-dashboard-budget`; it seeds 21 members, ten linked workspaces, and 50 activity records, then sends 200 isolated loopback requests. All measurement commands use disposable in-memory MongoDB and never modify a configured database.

For a failed or slow `InvitationAccepted` consumer signal, use `eventId` and `workspaceId` to inspect the queued event and its workspace document. Confirm the workspace is `ACTIVE`, then check `appliedEventIds`, `notAppliedEvents`, and membership state. A refusal should have `reason: ARCHIVED`; do not manually add a member for that event. A failed event can be retried safely because event receipt and membership/refusal are idempotent. Investigate any single-event duration above 5 seconds in MongoDB latency and queue backlog before retrying. The 5-second threshold is recorded in `enablers/observability/workspace/organization-alert-policy.json`; paging activation remains an external on-call decision.

Before applying the organization settings version migration to a persistent environment, follow the deployment's approved database-migration process and rehearse both `up` and `down` against a restored database copy. The recorded isolated-copy exercise is in `.project/01.1.03-S2-T1.md`; the migration only adds `version: 1` to legacy documents, and rollback removes that field. This repository does not configure a general-purpose migration runner.
For `409` lifecycle responses, reload the organization to inspect its current state before retrying. Archiving disables organization team-management writes at both the service and MongoDB update boundaries; reads remain available. Soft deletion removes the organization from organization lists and dashboard reads; it does not erase the persisted record. The repository has no first-class Workspace entity or workspace rename/write API, so downstream workspace writes cannot yet enforce archived-parent state. Cross-instance transition timing has not been measured; do not claim those guarantees until a workspace write surface exists and the distributed timing is tested.

For 401 responses, sign in again and confirm the session exists and has not expired. For 403 management responses, check the caller's organization role; only owners/admins may mutate team access. Invalid or expired invitation links require a fresh invitation to the matching account email. For 5xx responses or elevated error rate, inspect the dashboard's error rate and request logs, then check `/health` and MongoDB connectivity. For organization-list p95 above 700 ms, run `pnpm --filter @workspace/api measure:organization-budget`; it seeds 500 direct organization memberships for one principal, measures the first 50-item page across 200 loopback HTTP requests to `GET /organizations`, checks `member_list_page` in the explain plan, and writes a dated result under `servers/api/performance-results/`. Later pages are fetched by the list's scroll sentinel (with a keyboard-accessible Load more control); `nextOffset: null` means the list is complete and no further request is made. For setup p95 above 300 ms, run `pnpm --filter @workspace/api measure:organization-setup-budget`; it sustains 20 loopback `POST /organizations` requests per second for ten minutes against a separate in-memory MongoDB and records the result. For dashboard p95 above 700 ms or payload above 100 KiB, run `pnpm --filter @workspace/api measure:workspace-dashboard-budget`; it seeds 21 members, ten linked workspaces, and 50 activity records, then sends 200 isolated loopback requests. All measurement commands use disposable in-memory MongoDB and never modify a configured database.

## Security and isolation checks

`servers/api/features/workspace/tests/organization.gateway.test.ts` verifies owner and workspace membership scoping, deletion filtering, unrelated-tenant exclusion, sorting, and index use. `servers/api/features/workspace/tests/invitation-accepted.consumer.test.ts` verifies the new workspace collection is isolated by workspace ID, applies default/guest roles, suppresses replay, and records archived refusals. `servers/api/tests/collection-allow-list.test.ts` pins the current Mongoose collection set (`organizations`, `sessions`, `users`, `user_invitations`, `workspaces`). Organization command tests verify that missing, denied, wrong-action, and wrong-subject policy decisions cannot reach persistence.

`servers/api/features/workspace/tests/organization-settings.acceptance.test.ts` exercises
the settings update over HTTP and MongoDB: owner and member reads see updated defaults,
invalid values for all four fields are rejected without mutation and name their accepted
values, existing workspace data stays unchanged, simultaneous saves from one version
produce one update and one conflict, a member receives `403`, and the update emits a
labeled success signal with duration. Future workspace creation from organization defaults
and the `policy_denied_total` metric are not implemented in this module.
